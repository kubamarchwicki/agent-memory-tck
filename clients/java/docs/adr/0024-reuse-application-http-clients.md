# Reuse application HTTP clients through an internal transport seam

Applications configure their HTTP clients with observability (Spring observations and tracing, LangChain4j request logging) and network policy (proxy, TLS, timeouts, connection pooling), and memory calls should inherit both. The Java client therefore sends every NAMS exchange through an internal `HttpTransport` seam with three adapters: the JDK `java.net.http.HttpClient`, which remains the default, Spring Framework `RestClient`, and LangChain4j `dev.langchain4j.http.client.HttpClient`. This supersedes [ADR 0005](0005-use-jdk-http-without-a-transport-extension.md)'s prohibition of a transport seam and of injecting a configured client. ADR 0005's decisions against automatic retries and against a `MemoryClient` lifecycle method remain in force.

`HttpMemoryClient`, formerly `JdkMemoryClient`, continues to own routes, authentication, JSON processing ([ADR 0003](0003-optional-internal-json-adapters.md)), status and failure mapping ([ADR 0006](0006-use-client-owned-exceptions.md)), operation logging ([ADR 0021](0021-observe-operations-without-exposing-content.md)), and live-handle construction. The seam has one asynchronous operation. It sends a method, an absolute URI template with UUID or integer variables, headers, and optional body bytes, and it returns the status, case-insensitive multi-value headers, and body bytes without interpreting the status. The seam lives in `internal.http` and is public only for access across packages, as `JdkMemoryClient` was under [ADR 0022](0022-organize-packages-around-memory-operations.md). It is not a supported extension point, and supporting a third-party transport would require a later decision to publish it. A public transport SPI, which [ADR 0004](0004-verb-shaped-http-transport.md) proposed, was rejected: no code outside the artifact needs to implement the seam, and publishing an internal seam later breaks nobody, while withdrawing a public SPI would be a breaking change. One `MemoryClient` implementation per framework was rejected because it would duplicate route, failure, and logging code three times.

Applications pass an already built client to `MemoryClientConfiguration.Builder` through `jdkHttpClient(HttpClient)`, `restClient(RestClient, Executor)`, or `langChain4jHttpClient(HttpClient, Executor)`. The setters need distinct names because javac 17 must resolve the parameter types of every same-name, same-arity overload, so overloads naming both frameworks fail to compile when either framework is absent. Setters reject null immediately, the last setter called wins, and an omitted client falls back to `HttpClient.newHttpClient()` for each `MemoryClient.create(...)` call. `MemoryClient` keeps only `create()` and `create(MemoryClientConfiguration)`. The builder accepts built clients rather than framework builders so the library never mutates application configuration, and the library never closes an injected client or executor. The configuration remains the only source of the base URL and the Workspace API key: requests use absolute URLs and set their own `Authorization`, `Accept`, and `Content-Type` headers, and a `RestClient` base URL and default headers are not applied, so application-wide credentials or tenant headers never reach the memory service, while the injected client's interceptors still run and may add headers. Reflecting over the builder's methods fails with `NoClassDefFoundError` unless both frameworks are present; this is accepted because applications call the builder rather than introspect it.

`RestClient` and LangChain4j block the calling thread, so their setters require an application `Executor`. The JDK client runs dependent work on its own executor, which applications configure through `HttpClient.Builder.executor(...)`. Cancelling a returned future does not interrupt an exchange that is already blocking. The Spring adapter uses `exchange(...)`, so status handlers registered on the application's `RestClient` do not apply and non-success responses keep their headers. LangChain4j throws `HttpException` for non-success statuses and discards the response headers, so its `MemoryServiceException` carries the status and body excerpt with no headers or content type, and its operation events omit the request ID. This loss is documented, and the Spring adapter is recommended when those diagnostics matter. Every exception raised by a transport, including executor rejection and a synchronous failure inside the transport, completes the returned future exceptionally with a `MemoryClientException` that retains the cause. Building a transport request therefore no longer throws synchronously; [ADR 0023](0023-build-validated-client-configuration.md)'s base URL validation makes the previous synchronous case unreachable through the public API.

Route templates reach `RestClient` so that Spring observations tag `uri` with a template such as `/v1/conversations/{conversationId}` instead of `none`. Operation events move from the `org.neo4j.agentmemory.JdkMemoryClient` logger to `org.neo4j.agentmemory.MemoryClient`, and `event=client.initialized` reports `transport=jdk-http`, `spring-rest-client`, or `langchain4j-http`. The rename breaks existing logger configuration, which is acceptable before 1.0.

`spring-web` and `langchain4j-http-client` are optional dependencies of `agent-memory-client`, in the same way as Jackson. The core still runs without either framework. The Spring floor is Framework 7.0.0, following the Spring AI 2.x line: Spring AI 2.0.0 resolves to Spring Framework 7.0.8, Spring Boot 4.1.0, Jackson 3.1.4, and Java 17 bytecode. Spring 6.x is unsupported, partly because Spring 7 stopped implementing `MultiValueMap` in `HttpHeaders`. The LangChain4j floor is 1.0.0, which already provides every API the adapter uses. Verification covers the floors and Spring Framework 7.0.9 and LangChain4j 1.22.0. Framework wiring such as Spring Boot auto-configuration or a LangChain4j `ChatMemoryStore` remains downstream, as recorded in [ADR 0007](0007-keep-agent-workflow-orchestration-outside-core.md) and [ADR 0014](0014-keep-java-client-within-hosted-service-boundary.md). The [ADR 0013](0013-validate-traffic-against-published-openapi.md) contract suite runs once for each adapter.
